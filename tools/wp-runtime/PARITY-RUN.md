### Known harness limits

- Listeners never fire and DOM queries return empty: form injection, link decoration,
  WhatsApp append and consent flows cannot be exercised here (all explicitly out of scope
  in docs/WP-PARITY-DRAFT.md). This harness proves QUERY/REFERRER CLASSIFICATION parity only.
- The plugin writes through its full storage stack (cookie + localStorage mirror +
  sessionStorage fallback). We read the dataLayer push rather than re-reading storage, so
  storage-envelope bugs would not surface here.

## Observations from live execution

- **Click-ID ft_/lt_ mirror**: the plugin duplicates every captured click ID into
  `ft_<cid>`/`lt_<cid>` touch fields (`mapQueryFields` output goes through `applyTouch`,
  :1813-1837 + :1788-1799), while the TS engine stores click IDs top-level only
  (`mergeAttributionTouch`). Static analysis missed this. It only shows up in the five
  click-ID fixtures, which are all covered by rulings #1/#2 anyway, so those rows are
  marked RULED DIFF — but the storage-model difference itself deserves supervisor
  confirmation before Phase 2 freezes.
- **Timestamps compare exactly**: with the pinned Date the plugin emits the same
  millisecond ISO strings the engine stores (ruling #13 verified live, not just statically).

## POST-RULING RERUN (2026-08-23, work queue item #12)

Implemented the two runtime-finding rulings:

- **Ruling A (browser IDs, split responsibility)**: core parse now collects
  browser-ID keys (`fbc`, `fbp`, `ttp`, `li_gc`, `ga_client_id`,
  `ga_session_id`, `ga_session_number`) when they appear as URL QUERY PARAMS
  (`BROWSER_ID_PARAMS` in knowledge.ts; bare variant wins over `_`-prefixed,
  plugin preference order). `ga_client_id` is format-reduced to its last two
  numeric parts exactly like the plugin's `parseGaClientId` (:826-846). A bare
  `fbclid` derives top-level `fbc = 'fb.1.<epochMs>.<fbclid>'` when no explicit
  fbc exists (:860-866; deterministic via the injected clock).
  `mergeAttributionTouch` writes them top-level, newest non-empty wins.
  Cookie-derived IDs (`_fbp/_fbc/_ttp/li_gc/_ga*`) are collected ONLY by the
  /browser adapter (`src/browser/browser-ids.ts`, pure functions + seams)
  behind the consent gate — a denied gate means no cookie read at all. Core
  never touches cookies.
- **Ruling B (click-ID mirror)**: `mergeAttributionTouch` mirrors every
  captured click ID into `ft_<cid>` AND `lt_<cid>` at write time, matching
  `applyTouch(mapQueryFields)` (:1788-1799 + :1813-1837). The ft_ mirror sits
  inside the first-touch gate (plugin skips applyTouch('ft') when
  hasFirstTouch()); empty click IDs never overwrite existing mirrors.
